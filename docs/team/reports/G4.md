## Diseño propuesto: ficha honesta en 4 líneas/bloques verificables

Se propone extraer la tarjeta de cada especialista a un componente pequeño y testeable
`web/src/components/SpecialistCard.tsx` (con CSS propio `SpecialistCard.css` usando solo tokens existentes `--bg-elev`,
`--border`, `--fg-muted`, `--warn`, `--accent-ink`, sin semáforos falsos), usado desde `Specialists` en
`SettingsDialog.tsx`:

1. **Cabecera clara (identidad + modo activo real hoy):**
   - Chip existente (`<SpecMark id={s.id} /> {s.name}`) + dominio (`s.domain`).
   - Etiqueta sobria de **Modo actual** derivada exclusivamente del proveedor efectivo (`provider = specialist_bindings[s.id]?.provider_id || settings.default_provider`):
     - Si `s.id === "core"` y no hay adaptador personal activo: `Modelo base generalista` / `Generalist base model`.
     - Si el proveedor efectivo no soporta adaptadores (`capabilities_effective?.adapters !== true`):
       `Activo hoy: perfil por instrucciones (proveedor sin soporte LoRA)` /
       `Active today: instruction profile (provider does not load LoRA)`.
     - Si el proveedor soporta adaptadores pero el adaptador no está cargado:
       `Activo hoy: perfil por instrucciones (β) sobre modelo base` /
       `Active today: instruction profile (β) on base model`.
     - Solo si el proveedor soporta adaptadores **y** `s.adapter` consta cargado en `installed_adapters` del proveedor:
       `Activo hoy: adaptador LoRA cargado ({s.adapter})` /
       `Active today: LoRA adapter loaded ({s.adapter})`.

2. **Fila de fuentes de contexto activas (instrucciones y conocimiento):**
   - `Perfil base incluido` (siempre activo; si `s.sensitive === true`, nota sobria `Dominio sensible: incluye avisos prudenciales`).
   - `Instrucciones propias configuradas` únicamente cuando `(settings.specialist_instructions[s.id] ?? "").trim().length > 0`.
   - `Prompt optimizado activo (Evolution)` únicamente cuando el servidor informe una versión activa en `EvolutionStore` para `prompt:<id>`.
   - **Conocimiento recuperado:**
     - En `main` (antes de `codex/a9`): no mostrar contador ficticio por especialista; indicar con precisión
       `Memoria compartida global/proyecto (según ajustes de Memoria)` o mantener oculto el contador por especialista.
     - Con `codex/a9` integrado (o si el contrato del servidor devuelve `knowledge_docs: number | null`): cuando sea un
       entero, mostrar `Documentos del especialista: N` (`0` = `Sin documentos específicos cargados`).

3. **Estado honesto del adaptador de dominio y medición (`s.adapter !== null`):**
   Traducción completa `es`/`en` de `adapter_status` sin colores de éxito engañosos:
   - `planned`: **Adaptador planificado (`{s.adapter}`)** — *No entrenado ni medido con pesos reales en esta versión; el especialista responde mediante su perfil de instrucciones.*
   - `training`: **Adaptador en entrenamiento (`{s.adapter}`)** — *Sin evaluación de aceptación completada.*
   - `trained`: **Adaptador entrenado sin evaluación aprobada (`{s.adapter}`)** — *Existen pesos entrenados, pero no consta aceptación frente a criterios de dominio y no-regresión.* (Tono neutro/aviso, nunca insignia de éxito).
   - `evaluated`: **Adaptador evaluado (`{s.adapter}`)** — *Superó la evaluación registrada del catálogo* (aclarando igualmente si el archivo `.gguf` está o no instalado/cargado en este equipo).

4. **Desplegable `<details>` compacto «Requisitos del adaptador local» (para `s.adapter !== null`):**
   - Motor local `llama.cpp` (`spike-local` u otro servidor `llamacpp` con soporte `--lora`).
   - Modelo base compatible: `Qwen3.5-4B` (`base_model` del catálogo, GGUF).
   - Archivo de adaptador `<adapter>.gguf` en la carpeta local de adaptadores (`~/.spike/adapters/`), cargado al iniciar el motor local según la memoria disponible del equipo.

## Decisiones y opciones de contrato para Claude

Se presentan dos opciones compatibles hacia atrás (ninguna rompe clientes ni pruebas existentes):

- **Opción A — Solo frontend (cero cambios en Python):**
  `Specialists` en `SettingsDialog.tsx` consume los datos que ya tiene (`specialists`, `providers`, `settings`) más una
  lectura ligera al abrir la pestaña de `GET /api/runtime` (para saber qué rutas `.gguf` tiene configuradas el
  `LlamaServer` gestionado por SPIKE) y `GET /api/evolution/prompts` (para saber si hay prompt aprendido activo).
  - *Ventaja:* cero cambios en `spike/server/`.
  - *Límite:* si el usuario usa un `llama-server` externo (no arrancado con `/api/runtime/start`), `GET /api/runtime`
    devuelve `{"running": false}` aunque `AppState.installed_adapters[pid]` sí conozca los adaptadores tras probar el
    proveedor; además no sabría cuántos archivos `.gguf` hay en `~/.spike/adapters/` con el motor parado ni el recuento
    de `specialist:<id>` cuando entre `codex/a9`.

- **Opción B (recomendada) — Enriquecimiento aditivo de solo lectura en `GET /api/specialists`:**
  Mantener intactos todos los campos actuales de `Specialist.public()` (`catalog.py` no cambia) y añadir en el handler
  `GET /api/specialists` (`spike/server/app.py:411-414`) campos derivados del estado real en `AppState`:
  - `base_model: str` (`state.catalog.base_model`, hoy `"qwen3.5-4b"`).
  - `adapter_file_present: bool` (`bool(s.adapter and (adapters_dir() / f"{s.adapter}.gguf").is_file())`).
  - `loaded_on_providers: list[str]` (`sorted(pid for pid, names in state.installed_adapters.items() if s.adapter and s.adapter in names)`).
  - `learned_prompt_active: bool` (`state.evolution.store.active(f"prompt:{s.id}") is not None`).
  - `knowledge_documents: int | None` (`None` en `main`; cuando se integre `codex/a9`, número real de documentos en el
    scope `f"specialist:{s.id}"`).
  - *Ventaja:* 100 % exacto tanto con `spike-local` parado como con `llama-server` externo, una sola petición GET ya
    existente, trivial de simular en Vitest y pytest sin red ni modelos.
