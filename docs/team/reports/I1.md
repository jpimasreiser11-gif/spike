## Resumen

Implementado `python -m spike.launcher`: reserva un puerto loopback libre sin soltar el socket, espera a salud,
abre pywebview si está instalado o el navegador, impide dos lanzadores por SPIKE_HOME con un bloqueo del SO y
cierra el servidor, su llama-server y las tareas de descarga al salir. El asistente de primer arranque comprueba
disco y RAM, permite elegir adaptadores publicados, descarga únicamente al pulsar «Descargar todo», muestra progreso
y errores traducidos y configura los archivos verificados sin iniciar inferencia. Reutiliza y extrae el descargador
que ya usa el instalador mediante `spike models pull`, con SHA-256 y licencia obligatorios para el asistente.
Añadidos spec PyInstaller, staging offline comprobado, pins b11709 para seis plataformas y documentación de uso.
Código listo para revisión; no se afirma que exista un paquete nativo construido o probado con pesos reales.

## Decisiones

- No se toca `spike/desktop/`. El shell vive en `spike/launcher/`.
- El instalador de shell y PowerShell ya llaman al downloader de `spike.runtime.models`; se comparte esa
  implementación, conservando el comportamiento opcional del hash del CLI y haciéndolo obligatorio en el asistente.
- Todos los adaptadores del catálogo están `planned` y no traen repositorio/revisión/SHA publicados. El manifiesto
  `spike/launcher/adapters.json` queda vacío y la UI los identifica como perfiles de instrucciones sin adaptador
  descargable. La ruta de instalación de adaptadores seleccionados se prueba con una fuente HTTP falsa y un hash
  real de bytes de fixture. El manifiesto exige licencia permitida, commit inmutable, tamaño y nombre del catálogo.
- Se respeta la prohibición final de nuevas dependencias: no se añade el extra `desktop` ni se instala pywebview
  o PyInstaller. pywebview se detecta si ya existe; la spec también lo incluye solo si está instalado.
- El cierre normal de `AppState.close()` no detiene el runtime principal en este checkout. El lanzador envuelve
  su lifespan para detenerlo y esperar cancelaciones antes del cleanup existente, sin modificar el estado compartido.
- En navegador, cerrar la pestaña no informa al servidor: se proporciona «Salir de SPIKE» y Ctrl-C. Ese botón también
  cierra la ventana nativa después de terminar el servidor. Una segunda instancia se rechaza con mensaje es/en.
- No hay red al consultar estado. El POST de descarga requiere cliente loopback, JSON y origen exacto si existe;
  las rutas quedan inactivas en el servidor ordinario. No se aceptan URLs o destinos enviados por el navegador.
- Reservas conservadoras de instalación: 6 GiB de disco + dos veces el tamaño de adaptadores elegidos y 8 GiB de RAM
  total. Se muestra también RAM disponible; no son resultados de rendimiento ni una garantía de inferencia.
- Los pins de las seis variantes CPU se verificaron contra
  https://github.com/ggml-org/llama.cpp/attestations/56945604 (los Linux coinciden con `scripts/install.sh`).
  El staging no ejecuta binarios y la spec vuelve a comprobar plataforma, release y hashes de archivos.
