# Release Notes

1. Ask for the version, comparison range, intended readers and merged change evidence.
2. Group by user effect: additions, fixes, compatibility changes and known limitations. Omit unverified roadmap claims.
3. Explain the concrete trigger and resulting behaviour for each change; reference supplied issues when available.
4. Document required configuration or migration steps, including a safe rollback where the change needs one.
5. Distinguish automated checks from real-world measurement and release approval. Do not call a candidate published.
6. Deliver a concise draft with unresolved facts visibly marked for the release owner.

Respond in the user's language. Distinguish a draft from a verified deliverable.
